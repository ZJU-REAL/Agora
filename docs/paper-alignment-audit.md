# Agora 论文目标与实现审查

本文记录 P0 修复前的审查状态。后续修复及当前运行协议见
[P0 社会反馈闭环](social-feedback.md)；下列异常保留为历史复现依据。

审查日期：2026-10-26。依据当前主评测执行路径、调用点搜索和本地探针；没有调用外部模型，
没有采集真人或真实平台反馈。本轮为审查，未修改模拟和评分规则。

## 结论

可以沿用现有工程实现这版论文，但目前仅完成平台与评测基础设施，尚未完成“反馈驱动的跨语境
适应”实验。117 个工程回归通过证明接口与执行链路可用，不能证明模拟受众会理解内容、模型能
依靠反馈改善社会成效，或者模拟分数与人类判断一致。

| 论文要求 | 当前实现 | 判定 |
|---|---|---|
| 图文发布、评论与连续互动 | 三平台动作、媒体、Feed、多 tick | 工程可用 |
| 相同起点 | 冻结 Artifact、隔离数据库、版本校验 | 已有基础 |
| 相同预算、多 seed | tick/请求数/单次输出限制；episode seed 未应用到世界 | 部分完成 |
| 受众理解表达并给出反馈 | NPC 按概率点赞、固定模板评论 | 核心缺失 |
| 连续关系与信任积累 | Observer 分数累加，但不影响 NPC 行为 | 核心缺失 |
| 读取反馈并修正策略 | 可看当前 Feed；没有显式任务和行动结果历史 | 部分完成 |
| 负反馈后的适应评测 | 任务字段和粗略统计函数；未接入完整执行/报告 | 核心缺失 |
| 跨文化、跨垂域迁移 | 平台得分最强/最弱比值 | 不能据此认定迁移已实现 |
| 人类与真实反馈校准 | 人工标注导出、对齐统计 | 工具骨架，未完成校准 |

## 模拟逻辑

1. `oasis/agora_oasis.py:629` 的 `advance()` 按 Persona 固定概率决定是否点赞和评论。
   点赞目标主要由 Feed 名次决定；评论为“某人看到了这条内容并留下了回应”。帖子正文的语义、
   先前道歉是否兑现、用户价值观与文化规范，都没有进入反应策略。
2. 默认 scripted NPC 不会因为认可而自主关注、收藏，也不会因为失望而取消关注或提出具体异议。
   平台有这些接口，主环境行为策略却没有调用它们。`policy_type` 字段也没有在这里选择模型 NPC。
3. `benchmarks/runners/exclusive/runner.py:94` 的 `social_states` 是 Runner 内的评分状态。
   `sandbox.advance()` 不接收它；信任上升不会改变后续互动概率、评论或关系。
4. Observer 在 NPC 本轮实际行动前就评分，并遍历所有 NPC；没有按实际曝光筛选评估对象。
   因而“未看到内容也被判定受到影响”与“看到后真实回应”没有严格分开。
5. 事件日志已实现，但 `feedback_ticks`、`pressure_event_ticks` 等字段没有接入 tick 调度。
   `advance()` 没有负反馈注入或外部热点事件队列。固定内容池可以用于受控实验，但还不能支持
   关于真实平台热点发现与流量机制的结论。

需要补成：按实际曝光，为每个受众提供 Persona、文化/社群规范、与 Candidate 的关系历史及
当前内容，生成具体反应和公开行为；将关系状态写回环境，并影响后续行为。受众策略可以采用
规则或模型，关键是反应必须与内容和历史相关，并且经过独立的人类校准。

## AI 调用逻辑

已有 provider 工厂、JSON action、视觉输入、错误记录、模型身份和请求限制，能够发起模型调用。
缺失发生在模型获得的信息以及调用结果如何回到下一轮：

- `benchmarks/adapters.py:86` 每轮重新构造消息，没有保存跨轮对话。当前 Feed 可能携带部分
  先前帖子和评论，但不等于完整的行动历史与工具结果。
- `ExclusiveRunner` 传入 scenario ID、step、可用动作和素材；没有传入明确任务目标、账号约束、
  文化规范或剩余预算。`CreatorTask.objective` 没有接入该路径。
- 搜索、查看等动作返回的 `outcome` 被记录，却没有作为上一轮工具结果交给下一轮 Candidate。
  模型可能无法利用自己刚刚查询到的信息。
- `benchmarks/observers.py:21` 的模型 Observer prompt 仅含 action、outcome 和是否直接目标。
  不包含目标 Persona、文化规范、原始争议内容、前后对话或已有信任。不同受众可能收到完全
  相同的评分请求，无法支持受众特定的信任判断。
- 默认开发 Observer 匹配“谢谢、理解、确认、愿意、抱歉”等词；配置中不同名称的 scripted
  Observer 实际继承相同规则。不同名字不是独立评判标准。
- 请求数和单次输出上限不能完全等同于统一实验预算。总输入/输出 token、动作成本和续跑预算
  尚未成为可审计的统一约束；缺失 token usage 在报告中按 0 计也需要区分。

目标路径应显式传递任务、可见反馈、行动/工具结果历史和剩余预算；受众模型与评测 Observer
分别定义职责。隐藏关系状态可供环境和评估使用，但不直接泄露给 Candidate。

## 评测逻辑

### 社会成效和反馈适应

`benchmarks/metrics/report.py:70` 主要加总 Observer 的四维变化。
`dialogue_progress` 直接等于态度增量，`timing_judgment` 依据 scenario ID 是否含 bait/spam
判断是否应该全程不行动，尚不能当作独立验证过的模型能力指标。

`benchmarks/metrics/creator.py:26` 虽然提供创作者统计，但 `write_run_report()` 未调用它。
其中 `feedback_adaptation` 只是最后一条帖子与第一条帖子的最终互动量之差，没有定位负反馈、
确认改动针对反馈、控制曝光或排除 Candidate 自己的评论。它不能证明模型利用了反馈。

第一阶段应分别报告：

- 行为结果：真实曝光人数、独立受众点赞/收藏/回复/关注及退出，按曝光或机会归一化；
- 关系结果：认可、信任、继续互动意愿的变化，由校准后的独立判断支持；
- 适应结果：负反馈后是否定位问题并调整，以及后续关系与行为是否改善；
- 执行能力：动作是否合法、工具结果是否被正确利用，避免与社会成效混成一个总分。

加入正常反馈、隐藏反馈、打乱反馈等受控条件。在相同任务和曝光条件下比较恢复轨迹，才能
区分“恰好后面表现更好”与“利用反馈取得改善”。点赞和热度也不应直接代替信任。

### 跨语境迁移

`benchmarks/metrics/cross_cultural.py:22` 仅取不同平台最高分与最低分，再计算比值。
没有 source/target 配对，没有垂域或文化标识，没有适应阶段或历史传递。
平台、语言、文化和任务难度的变化目前混在一起。

应建立明确的语境字段和配对场景：平台、语言、社群文化、垂域、受众构成及反馈规范。
先在同平台控制其他变量，再改变文化或垂域。明确迁移的是模型的零样本能力、源语境形成的
上下文经验，还是允许目标反馈后的适应策略；三者分别报告。

对每个目标语境，在同一评分尺度上比较首次表现、固定反馈预算后的表现、原生目标语境基线，
以及源语境经验是否有帮助。使用配对差值和恢复曲线；不要把最弱/最强的平台分数比直接称为
迁移损失，尤其是社会状态分数可以为负或接近 0 时。

### 校准

`benchmarks/calibration.py:132` 导出的标注文件包含 simulated_score、评委 ID，以及由 run 目录
生成的 item ID，不能直接作为盲评材料。需要把标注材料与私有对齐表分开，并随机化标识和顺序。

已有相关系数、方向一致率和误差统计，但没有真实数据的授权来源/采样/划分和闭环验证流程。
真实反馈是校准数据，不会自动证明沙盒结论可外推到真实平台。需要按文化/垂域分层检查，保留
独立验证集，并分别标注模拟结果、人类判断和真实反馈。

## 本地复现的异常

使用一次性本地探针，未发起网络模型请求：

1. 初始世界 seed=73，两个 episode 分别声明 seed=1/2；实际数据库 seed 均为 73，NPC 顺序均
   为 `[2,4,3,5]`。Runner 没有将 episode seed 应用到环境，当前多 seed 不等于环境随机重复。
2. 在相同概率、排名和受众下，友善修正与敌意拒绝两条内容均获得 1 个赞和相同的固定评论。
3. 向模型 Observer 提供不同 target、Persona 和 culture，实际发送的请求仍完全相同。
4. 向 JsonModelCandidate 的 context 提供 objective/culture/previous_actions，实际 prompt
   没有这些字段。
5. 人类分数为 `[-1,1]`、模拟评委恒为 `[0,0]` 时，校准函数输出 Spearman=1.0、方向一致率=0、
   MAE=1.0。原因是 `_pearson()` 对零方差返回 1.0；这种情况应报告不可计算或明确失败状态。

这些问题没有被现有工程测试覆盖。本轮保留原实现，避免在审查过程中未经区分地改变实验协议。

## 补齐顺序与验收

1. **先完成单平台反馈闭环。** 明确任务和语境输入、行动/结果历史、内容相关受众策略、关系
   状态回写、曝光后判断、可调度负反馈。修复 seed 与统一预算，形成可复现的完整运行。
2. **再完成反馈适应评测。** 将任务字段和指标接入 Runner/报告；同一场景运行正常、隐藏和打乱
   反馈条件，能追踪某条负反馈、Candidate 修正与后续结果。
3. **再完成跨语境协议。** 文化与垂域分离，冻结 source/target 配对，明确是否保留源经验，输出
   目标语境首次表现、适应表现、迁移差值和恢复曲线。
4. **最后完成校准与正式实验。** 修复盲评导出和退化统计，冻结独立评委池，收集目标社群的人类
   判断和经授权的真实反馈，在独立验证集确认有效性后比较模型。

第一阶段可以聚焦“发布或回应 → 遭遇具体负反馈 → 调整 → 持续互动”的受控任务。热点发现、
商业流量和全量账号运营可单列后续实验，不需要现在合并成总分。
